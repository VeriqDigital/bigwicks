# Milestone 6A: pre-release security audit

Audit date: 2026-09-07. Repository: Big Wicks. This is an assessment of a fixed source baseline and fictional local deployments, not certification of a deployed service.

## A. Executive assessment

**Patch Next.js before an Internet-facing release.** The installed and locked `next@16.2.9` is affected by a published unauthenticated denial of service in App Router applications with Server Actions. This application meets those conditions. Application authorization and its database rate limits do not resolve a framework-level request-processing flaw. The current primary-source review also found a later critical Windows-hosting advisory that the npm bulk response did not include. See SEC-01 and SEC-02.

**The public contact action has a reproduced email-abuse path.** Valid anonymous requests can be repeated and each initiates a distinct provider operation. A honeypot, form validation and Origin checking do not stop a client deliberately submitting valid requests. Resolve SEC-03, or verify an effective upstream control before enabling this public email route.

The audit reproduced two narrower concurrency concerns: independently confirmed invitation batches, including an individual send overlapping a bulk send, can send competing setup links; and an already-authorized admin operation can cross a subsequent admin-revocation boundary. The former is an onboarding reliability defect (REL-01). The latter is a limited in-flight revocation gap (SEC-04), not a way for a newly disabled admin to start authenticated operations. These do not establish an anonymous account takeover.

The completed tests and source traces found no demonstrated cross-customer order disclosure, cross-tier pricing disclosure, forged order price/owner acceptance, create-only import overwrite, reusable consumed account token, or public registration path. These conclusions apply to the tested paths, not to every possible input or production configuration.

## B. Architecture and attack-surface map

### Trust and data paths

The public site and anonymous account entry points reach Next.js Server Actions and Auth.js handlers. Credentials and account tokens are verified against PostgreSQL. An encrypted JWT carries identity and `sessionVersion`; database reads determine current role, active state and customer association. Protected services call authorization themselves rather than relying on a layout.

Sanity supplies intentionally public product/category content. PostgreSQL supplies private customer accounts, independent tier prices and order snapshots. The customer catalog joins the current customer's tier with validated published content and returns an explicit DTO. Order submission obtains authoritative prices and identity again, commits immutable SQL snapshots, then attempts a staff notification through Resend. Studio has both the website ADMIN gate and Sanity's separate account/dataset permissions.

Operator CSV/XLSX tools are a different trust boundary: a person with filesystem and explicit service credentials supplies files and reviews target-bound plans. Offline preparation does not need remote credentials. Remote catalog mutation, production provisioning and live configuration were source-reviewed only.

### Security properties traced beyond the entry-point guards

**Authentication and tokens.** `auth.ts:15-28` ignores client session updates and resolves the current principal; `lib/auth/principal.ts:21-35` rejects disabled, stale, malformed and inconsistent domain associations. Login normalizes email, caps email/password length and performs a dummy Argon2 check for unknown eligible inputs (`lib/auth/credentials.ts:14-25`, `lib/auth/password.ts:1-22`). Argon2id uses 19 MiB, time cost 2, parallelism 1; choosing a password requires 15–128 characters. Limiting precedes expensive work. Uniform failure text and deferred reset eligibility reduce enumeration; no claim of statistically constant network timing is made.

Session lifetime is eight hours. Default Auth.js cookies are HttpOnly, SameSite=Lax and host-scoped; Secure behavior depends on HTTPS/configuration. Logout clears the current cookie, not every stolen copy. Email changes, password changes, disables and re-enables increment SQL sessionVersion, so old JWTs do not revive. A read already authorized and downloaded cannot be recalled from the browser; server checks govern fresh requests.

`lib/auth/account-tokens.ts:16-104` uses 32 random bytes encoded as hex, SHA-256 storage, purpose, 24-hour setup/one-hour reset expiry, delivery marker, version and consumed state. Token writers lock User first, then inspect current state. Password hashing occurs outside the lock, followed by full in-transaction revalidation. Simultaneous consumers produce one password update; a reissue consumes prior tokens of that purpose. Disabled-account password choice never flips either active flag or creates a session. Bulk invitations intentionally require active accounts; individual setup/reset retains the documented disabled-account policy.

Preview encryption uses AES-256-GCM with random 12-byte IV, purpose-domain key derivation/AAD, canonical base64url and bounded payload parsing: `lib/orders/review-token.ts`, `lib/pricing/preview-token.ts:14-39`, `lib/admin/customer-batch-token.ts:16-40`. Orders bind user/customer/version and expire after 15 minutes; pricing and customer previews bind admin/version/current state and expire after ten minutes. Cross-purpose/tampered/expired/wrong-principal previews are rejected. These require a sufficiently random, stable and environment-specific AUTH_SECRET.

**Web request boundaries.** Installed Next.js compares Origin with Host or the forwarded host and blocks mismatches; the audit HTTP test proves mismatched and literal `null` Origins do not send contact mail. Missing Origin is permitted with a warning in this installed implementation, so Origin is not bot authentication. Normal cross-site browsers remain constrained by Origin checking, SameSite cookies and Auth.js CSRF. Trusted-ingress rewriting and canonical AUTH_URL are necessary deployment assumptions; spoofed forwarding at a live ingress was not tested. Auth.js's fixed dispatcher prevents browser callback URLs from choosing arbitrary post-login destinations. Setup/reset links use validated AUTH_URL, not request headers (`lib/auth/account-email.ts:4-15`).

Node Server Actions use the installed default 1 MiB body limit; application upload checks run after framework request decoding and before reading/parsing the uploaded file. No Edge runtime, custom server, proxy/middleware authorization, custom rewrites, or added action `allowedOrigins` configuration was found. Those defaults do not mitigate SEC-02.

**Catalog and private reads.** `lib/catalog/content.ts:7-22` selects an explicit published field projection, uses no read token, disables the Sanity CDN and Next cache, sets a ten-second timeout and disables retries. Normalization rejects malformed/ambiguous identities and bounds normalized document count; it is not a streaming byte cap before the Sanity response arrives. Current SQL tier prices are joined only after customer authorization, with an explicit DTO (`lib/catalog/service.ts:14-42`). Private routes built dynamically. No shared application price cache, public price endpoint, query-selected identity/tier or secret-bearing metadata was found. A trusted editor's large catalog/admin account list remains a capacity concern, not a demonstrated anonymous arbitrary-query path.

Confirmation authorization is `reference AND current customerId`, not reference entropy. Admin reads independently authorize. A same-tier customer's direct HTML/RSC response contained no owner marker; streamed Next.js denial can legitimately use HTTP 200 with `NEXT_HTTP_ERROR_FALLBACK;404`. Status alone is not evidence of disclosure.

**Orders and money.** `lib/orders/input.ts:3-40` bounds selection to 250 distinct UUID identities, integer case quantities 0–999, excludes zero lines and uses exact BigInt cents. Submission re-resolves current identity, active flags, association, tier, product identity/content and prices (`lib/orders/service.ts:21-44,71-128`). Serializable SQL locks User then Customer; the database unique customer/submission key and nested item insertion prevent duplicate/partial persistence. The ten-order/hour count is checked within the serialized operation. Input prices, totals, owner, role or tier are never authoritative. Changed reviewed material generates a renewed review with the same submission identity, without creating an order.

Saved-token recovery checks for an existing order before rejecting expiry, but still requires a current authorized caller and matching sealed review hash. An unused expired token cannot create an order. A saved retry does not send another staff notification. Historic snapshots are read from SQL, not reconstructed from current Sanity/pricing/customer fields, and there is no application order-edit/delete action.

Sanity and PostgreSQL cannot share this transaction. A Sanity edit after the final content fetch can race the SQL commit; SQL serialization also does not promise the latest wall-clock value of an overlapping transaction. This is a documented boundary of reviewed order requests, not live stock reservation. An operational pause during import/publication and renewed review for detected changes are the relevant controls.

**Notification semantics.** `lib/orders/service.ts:107-122` saves before sending; `lib/orders/email.ts:18-29` uses a fixed recipient, plain text, ten-second timeout and a stable order-reference idempotency key. Provider acceptance is recorded as ACCEPTED; known failure as FAILED; interrupted/uncertain status persistence can leave PENDING. A crash before the send can leave a saved order without an attempted email. A timeout after provider acceptance is uncertain. Replaying the saved order recovers its reference and does not retry notification. There is no durable outbox/reconciler and no exactly-once inbox guarantee. This agrees with `docs/ORDERING.md:143-169`; staff must monitor the authoritative order list. Account emails likewise become usable only after acceptance is recorded; a provider-accepted email can contain an unusable link if status storage fails or another issuance supersedes it.

**Imports.** Customer CSV accepts exactly five columns, up to 128 KiB/250 rows/2,048-character records, strict UTF-8, explicit field bounds and control-character checks. It accepts no roles/passwords/hashes/tokens, cannot update an existing identity/admin, keeps both active flags consistent and never sends email. Preview and confirmation compare bounded current customer/user/tier snapshots; the serializable confirmation locks/rechecks the acting admin inside its transaction. Database uniqueness and rollback protect concurrent conflicts (`lib/admin/customer-import-csv.ts`, `lib/admin/customer-import.ts:11-69`, `lib/admin/customer-create.ts:7-16`).

Pricing CSV is bounded to 256 KiB/500 rows/4,096-character records and exact current rank/name tier columns (`lib/pricing/csv.ts:7-58`). Blank prices mean removal with acknowledgment, not zero or copied-tier pricing. Numeric text with excess scale is rejected, not rounded. Formula-leading human text, including whitespace/fullwidth variants, is escaped in quoted BOM/CRLF CSV (`lib/pricing/csv.ts:60-68`). Product name/SKU are informational; catalogKey is authoritative. Confirmation repeats current content/SQL/tier comparison under a serializable transaction with an acting-admin lock (`lib/pricing/service.ts:51-88`). Customer/pricing replay is constrained by changed state; an unchanged pricing no-op is not a duplicate destructive mutation.

**Operator parsing and mutation.** Local input is bounded to 2 MiB and regular files; output is restricted to resolved `data/onboarding` paths, simple filenames, exclusive creation and no overwrite (`scripts/onboarding/files.ts:6-56`). Parser tests cover malformed UTF-8/CSV/control characters and identity collisions. XLSX parsing has at most 64 ZIP entries, 4 MiB per entry/8 MiB total expanded data, one expected sheet, bounded rows/columns, rejected formulas/DTD/entities, a 128 MiB JavaScript heap and a 15-second worker deadline. The subprocess receives a short system-environment allowlist, no service secrets or inherited NODE_OPTIONS (`scripts/onboarding/boxhero.ts:23-48`, `scripts/onboarding/xlsx-worker.mjs:1-51`). Native memory is not an absolute 128 MiB RSS ceiling.

Numeric XLSX selling-price/quantity cells use the documented spreadsheet numeric-artifact normalization; text/CSV money remains strict. Numeric identifiers retain identity text. Unit Cost and BoxHero-generated SKU do not enter mapped Sanity fields; quantity is not a live-inventory connection; independent prices stay in the private pricing artifact. Mapping hashes bind material derived choices, not merely the original input bytes.

Catalog plans cap 1,500 documents and 3 MiB mutation data, inspect raw drafts/releases and ambiguous keys/categories/SKUs, bind exact target and reviewed state, and allow only public content mutation fields (`scripts/onboarding/plan.ts:15-117`). Existing products use revision guards; new IDs are generated by Sanity rather than fabricated from catalogKeys. Category commit, reread and product commit are separate steps. Sanity lacks a database uniqueness constraint for a custom catalogKey: concurrent writers can still create conflicting new identities. `docs/ONBOARDING.md:338-343` explicitly requires a single operator and paused concurrent edits. Uncertain commits require inspection and a new dry run. Online imports were not executed.

## C. Prioritized findings

### SEC-01 — Critical Next.js advisory applies to Windows-hosted servers

**Severity:** Critical when network-accessible on a Windows filesystem. **Confidence:** High in affected version/configuration; production hosting applicability unverified. **Status:** Source-verified dependency condition; no RCE payload executed.

- **Locations:** `package.json:33-35`; `package-lock.json:16297-16349` (`node_modules/next`, installed/locked `16.2.9`); `next.config.ts:3-17` (App Router without Cache Components); `package.json:9-11` (standard Next server commands).
- **Advisory/preconditions:** [Maintainer GHSA-p293-qw3h-jr36 / CVE-2026-75604](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36), published August 25. Affected `>=13.4 <15.5.24` and `>=16.0 <16.3.3`; fixed `15.5.24` / `16.3.3`. Requires a Windows-hosted Pages/App application without Cache Components and network access to it.
- **Observed/intended/impact:** The audit host is Windows and the source matches the framework configuration. The local audit server was loopback-only. The intended release is documented around Vercel; no live host was inspected. This is conditional potential server code execution, not evidence that the intended Linux deployment or a real service was compromised.
- **Mitigations:** Local-only binding limited the audit exposure. ADMIN/customer checks do not repair filesystem request processing. The maintainer lists no workaround for an affected Windows host.
- **Smallest fix:** In a separate patch, move Next and matching `eslint-config-next` to a supported same-major patched version, at least `16.3.3` for these advisories; review the resolved lockfile and image dependencies. Do not expose the current Windows server publicly while pending.
- **Regression:** Clean sanitized build, existing auth/actions/ordering suites and supported hosting smoke checks after upgrading. Do not add a destructive RCE test to the normal suite.
- **Launch:** Blocks Windows network hosting. The same upgrade is independently required for SEC-02 on the application's general release path.

### SEC-02 — Public App Router Server Actions use a framework version with unauthenticated CPU denial of service

**Severity:** High. **Confidence:** High. **Status:** Source-verified; intentionally no CPU-exhaustion payload.

- **Locations:** `package.json:33-35`; `package-lock.json:16297-16349`; `app/contact/actions.ts:1-18`, `app/(portal)/login/actions.ts:1-22`, and the other Server Actions listed in B; `next.config.ts:3-17`.
- **Advisory/preconditions:** [Maintainer GHSA-m99w-x7hq-7vfj / CVE-2026-64641](https://github.com/vercel/next.js/security/advisories/GHSA-m99w-x7hq-7vfj). Relevant affected range `>=16.0.0 <16.2.11`, fixed `16.2.11`; the older branch fix is `15.5.21`. An App Router application with at least one Server Action meets the published condition. This repository exposes several, including public actions.
- **Observed/intended/impact:** Installed and locked `16.2.9` is affected. A crafted request can consume excessive CPU and obstruct other requests in the process. Normal bounded action processing and application quotas cannot be relied upon to constrain this vulnerable framework path.
- **Evidence/mitigations:** Verified actual installation, lockfile, App Router/actions and the maintainer's condition. SQL login/order quotas, Origin checks and hidden admin controls do not address the underlying parsing/processing problem. No framework workaround is listed.
- **Smallest fix:** The isolated framework/dependency patch from SEC-01; `16.2.11` alone is insufficient for the later advisories reviewed here. Regenerate the lockfile deliberately and verify transitive versions without `audit fix --force`.
- **Regression:** Full applicable existing unit/SQL/browser suites, sanitized configured/unconfigured production builds, direct action CSRF/authorization and order-response recovery checks. Requery official advisories on the selected exact version.
- **Launch:** **Yes**, for an Internet-facing release with these actions. This is not contingent on guessing live WAF settings.

### SEC-03 — Valid anonymous contact submissions create unbounded distinct email attempts

**Severity:** Medium. **Confidence:** High. **Status:** Reproduced through function calls and a local production HTTP Server Action.

- **Locations:** `app/contact/actions.ts:19-63` (input/honeypot), `65-76` (configured activation), `90-120` (fetch/new idempotency key/no timeout); `tests/security/reproductions.test.ts:38-49`; `tests/security/http.spec.ts:7-30`.
- **Attacker/preconditions:** Anonymous client can load the public contact form and send valid bodies with a blank honeypot. RESEND/contact sender/recipient configuration is enabled. No effective upstream per-source/aggregate protection is established by this repository.
- **Observed versus intended:** Six identical bounded calls initiated six fetches with six distinct idempotency keys. On the local production build, one real form POST plus two replays initiated three captured emails. Mismatched and `null` Origins were blocked, demonstrating that those checks work but do not stop direct or same-origin abuse.
- **Impact:** Staff inbox flooding and consumption of email quota/cost. This path uses the same RESEND_API_KEY variable as account/order mail, so shared-provider capacity can affect business notifications. The fetch also has no AbortSignal deadline, increasing exposure to a stalled provider; no real provider hang/load was induced.
- **Existing mitigations:** Length limits, inquiry enum, fixed recipient and plain text prevent several injection/open-relay variants. The honeypot only catches cooperative bots; fresh random idempotency keys explicitly make replays distinct. Client button state is not a server limit.
- **Smallest fix:** Add a shared server-side allowance before outbound work and an explicit short transport timeout. Select source identity only after establishing trusted ingress; bound aggregate mail volume as well as individual sources. Keep safe field validation, fixed recipient and generic failure feedback. An upstream rule can be an interim control only if direct action POSTs demonstrably traverse it. Consider challenge escalation if needed; do not assume a CAPTCHA alone is required.
- **Regression:** Over-limit/concurrent/replayed attempts must stop before transport, a stalled transport must return within its deadline, rejected inputs/honeypots must not send, and valid limited requests must still succeed. Preserve the Origin assertions. The audit observation currently asserts vulnerable behavior and must be inverted when fixed.
- **Launch:** Conditional blocker for enabled public email absent verified equivalent ingress control. Disabling mail configuration currently gives explicit unavailability; it is not a working contact-email release.

### REL-01 — Overlapping invitation operations can send competing setup links

**Severity:** Medium reliability; low security impact with an already-authorized admin. **Confidence:** High. **Status:** Reproduced with controlled barriers and real disposable SQL.

- **Locations:** `lib/admin/customer-invitations.ts:42-71`, especially snapshot checks at `46-48,59-64`; `lib/auth/account-tokens.ts:31-61`; `app/(portal)/admin/customers/invite-action.ts:11-26`; `tests/security/reproductions.test.ts:50-68,91-111`.
- **Access/preconditions:** Two valid distinct previews overlap on a recipient, or a bulk confirmation overlaps an individual send. This can be ordinary double-tab/multi-operator behavior; anonymous users cannot invoke the admin send service.
- **Observed versus intended:** Barrier tests pause both callers immediately before `issueAccountToken`, after their checks. Releasing them lets both use the real recipient User lock, issue/supersede and attempt delivery. Two emails are captured; only one unconsumed delivered token remains. The shared three-per-recipient allowance works: a subsequent third send is allowed and the fourth is denied. It does not coalesce these first overlapping attempts.
- **Impact:** A customer can receive an already-superseded link, with arrival order potentially making the last email misleading. Staff may see an accepted result that later becomes superseded. This is not two usable passwords/tokens or an access bypass. The existing result language correctly distinguishes acceptance from inbox delivery; aggregate output is not a durable campaign ledger.
- **Why existing controls fall short:** The preview claim prevents replay of the same ciphertext, not independently sealed previews. Fingerprint checking is outside the issuance transaction; the issuer verifies email/active/version but not the previewed latest-token state. Per-request 600 ms pacing also is not an aggregate cross-request provider rate guarantee.
- **Smallest fix:** Carry a reviewed per-recipient token-state version into issuance and compare/claim it under the same User lock used to supersede tokens. A competing operation whose expected state has changed should return a clear stale/not-attempted result before creating a token or sending. Integrate individual sends with the same mechanism; allow intentional later resends through a fresh review. Consider a per-recipient durable attempt claim without holding a SQL transaction open during provider I/O.
- **Regression:** Distinct overlapping previews, partially overlapping lists, individual-versus-bulk, reverse provider completion order, shared quotas and explicit later resend. Assert delivery attempt count and which links remain usable, not only same-preview replay or final token count.
- **Launch:** Blocks unrestricted concurrent real campaigns until fixed. A documented single operator with one in-flight send flow is a practical interim operational restriction, not a code-level fix.

### SEC-04 — Acting-admin revocation is checked before, not atomically with, some operations

**Severity:** Low for the demonstrated in-flight window; higher operational significance if immediate revocation is a required incident-control guarantee. **Confidence:** High in behavior, policy interpretation requires a decision. **Status:** Reproduced.

- **Locations:** `app/(portal)/admin/customers/actions.ts:65-127`; `app/(portal)/admin/customers/invite-action.ts:11-20`; `lib/admin/customer-invitations.ts:51-64`; `lib/auth/account-tokens.ts:31-47`; comparison: `lib/admin/customer-import.ts:11-14,53-69`; tests `tests/security/reproductions.test.ts:69-81,112-123`.
- **Access/preconditions:** The actor must be valid ADMIN when the action/service guard runs. A separate operation then disables/revokes that actor before the customer transaction or token issuance begins. A fresh already-revoked request is rejected.
- **Observed/intended:** An audit spy commits admin `active=false` and increments its sessionVersion after `editCustomer`'s guard, before its transaction. The customer edit still commits. Another test revokes the actor at entry to the bulk token issuer, after its per-recipient check; one mail attempt still occurs. Serializable isolation around the target customer cannot serialize an actor row that it never reads/locks. Bulk authorization transactions release their locks before the send operation.
- **Impact:** An operation already authorized in flight can finish after revocation, including a selected customer edit or one invitation. This is a bounded revocation-consistency limitation, not proof of durable access by a disabled admin. Ordinary request-time authorization may be an accepted policy; documentation should not be interpreted as cancellation of every in-flight operation.
- **Mitigations:** Guarding every new action and rechecking each bulk recipient prevents starting new authorized work and stops later iterations after revocation is observed. Customer import and pricing confirmation already check/lock the acting admin inside their write transaction.
- **Smallest fix if strict commit-boundary revocation is required:** Preserve the actor principal, lock/recheck it within individual mutation transactions using the existing helper pattern, and bind acting-admin state into the token-issuance transaction. Define an operation linearization point; an external send after a committed claim cannot be perfectly recalled by a later revocation. Do not promise instantaneous cancellation of provider delivery.
- **Regression:** Controlled guard-to-transaction and per-recipient-check-to-issuance revocation barriers; no mutation/claim when revocation won; valid in-flight operation can commit when its lock/claim won first. Test lock order/deadlocks as part of the change.
- **Launch:** Not a blanket launch blocker under request-time authorization. Record the accepted semantics or fix before relying on immediate revocation as a release/incident guarantee.

## H. Residual risk and limitations

This assessment establishes source-level paths, selected adversarial invariants and bounded local reproductions on the recorded commit. It does not establish that a deployed system has the same source/configuration, that all dependencies are vulnerability-free, or that every race/malformed input is covered. Dependency feeds change and can lag primary advisories, as the Next comparison demonstrated.

No deployed endpoint, private environment file, real customer workbook, remote SQL/Sanity/Resend state, DNS record, account membership, provider dashboard, production backup or monitoring sink was inspected. Production TLS, cookies through actual ingress, cache behavior, deployment OS/native binaries, action duration limits and delivery remain unknown. Configured Studio mounting against a real project and Firefox order behavior were not completed. Google Fonts responses were mocked for successful builds, so this audit does not certify visual/font behavior.

The service-level concurrency tests use controlled injected barriers around existing function/transaction boundaries; they prove the observed interleaving is possible, not its real-world frequency. They deliberately preserve the actual token/SQL/limiter operations. No high-load, CPU bomb, malicious native-image, RCE or live brute-force test was run. No penetration-testing claim is made for external services.

Read-time authorization cannot retract data from a previously authorized browser or mail recipient. SQL and Sanity cannot provide a shared atomic snapshot; provider acceptance cannot guarantee inbox arrival; committed external work cannot be recalled instantly on revocation. The documented single-operator catalog constraint, staff notification monitoring and live release controls remain material parts of the system's security and reliability.
